# Agent instructions — Ora

This document provides context and conventions for agents modifying the project. User and harness instructions take precedence.

## Purpose and stack

Ora is a time-tracking app for projects, teams, and people. Stack: Next.js 16 App Router, React 19, TypeScript 5.9, ESLint 10, Tailwind CSS 4, Prisma 7/SQLite with the better-sqlite3 driver adapter. APIs are route handlers under `src/app/api`; authentication uses bcryptjs passwords and signed session cookies. Excel files are generated with ExcelJS.

## Structure

- `src/app/(app)/`: protected app pages (timer, timesheet, and management); `/projects` is available to all roles, and all roles may manage project member assignments while Owner/Admin retain team, archive, and deletion controls. Complete Excel backup is Owner-only; offline SQLite snapshot/restore remains an administrator-run Windows operation.
- `src/app/api/`: API route handlers; `api/export/route.ts` handles filters, CSV ZIP/Excel multi-sheet grouping, and export columns. `api/version/route.ts` provides manager-only update status from GitHub Releases. `api/update/route.ts` exposes manager-only update trigger/status over the local updater broker.
- `src/components/shell.tsx`: shared authenticated layout, header, side panel, and theme controls; shows the manager-only Ora server release/update controls. Desktop client release notices are a separate, all-authenticated-user feature and must not invoke the web-service updater. The mobile navigation drawer traps keyboard focus, closes on Escape, and restores focus to its trigger.
- Shared desktop-parity views: `src/components/projects-view.tsx`, `timer-view.tsx`, and `my-hours-view.tsx` receive typed API adapters. Keep web fetch adapters in the route pages and desktop adapters under `src-tauri/`; the Tauri client must remain constrained by `desktop-api.ts` and the server allowlist.
- `docs/desktop-parity-inventory.md` maps web routes/actions to the approved desktop scope and current API coverage, specifies server-profile onboarding/per-origin credential isolation, records minimum safe API gap resolutions, and recommends shared React feature views with separate web/Tauri adapters; update it as parity work changes. `docs/desktop-phase5-plan.md` records approved desktop distribution and operations decisions, release metadata/UI/uninstall flow, and validation boundaries. `docs/desktop-release-checklist.md` also tracks the proposed full web-app parity phase; the desktop remains a reduced panel with a deliberately limited API contract until the product scope, authentication, and authorization decisions are approved. `/api/desktop-release` serves marked stable GitHub desktop releases to authenticated users, separately from server updates. `.github/workflows/desktop-release.yml` is `workflow_dispatch`-only and attaches MSI/NSIS plus SHA-256 manifest to an existing marked release. `scripts/publish-release.ps1` updates server and desktop versions together and dispatches it after publishing; local installer packaging succeeded, but workflow execution and installer lifecycle tests remain unverified.
- `src/components/ui.tsx`: shared UI components (`Input`, `Select`, `Checkbox`, `Textarea`, buttons, cards, and headers). Date inputs use the native date picker, themed through CSS `color-scheme`. Interactive controls should retain visible keyboard focus, named icon-only actions, and exposed selection states; native selects use shared theme-aware glass styling with readable options. Floating menus and modals should use more opaque theme-aware surfaces and dimmed backdrops to preserve legibility over underlying content. `globals.css` honors `prefers-reduced-motion`.
- `src/app/globals.css`: design tokens and theme presets. When changing token palettes, verify text/status and button foreground/background contrast; normal text should meet WCAG AA (4.5:1).
- `src/lib/app-config.ts` and `src/lib/server-config.ts`: centralized access to public and server-side configuration defined in `.env`; `.env.example` documents the keys. Avoid direct `process.env` access elsewhere. `public/ora-logo.svg` is the editable vector source for the default transparent `public/ora-logo.png`; configured custom light/dark logos override the default in web UI, while Ora Desktop uses the default assets in `src-tauri/icons/` and `public/ora-logo.png`. Keep both Tauri package icons (PNG/ICO) synchronized with the default mark.
- `src/lib/updater-ipc.ts`: client for the local named-pipe updater broker; sanitizes statuses before returning to the app. The web process must not elevate or replace itself or its own service.
- `src/app/api/deletion/route.ts`, `src/lib/deletion-ipc.ts`, and `/manage/uninstall`: Owner-only control for the separate `OraTimeTrackingDeletion` broker. Requires the full Excel archive download and `YES` confirmation; all text is localized.
- `src/i18n/messages.ts` contains the typed English, Italian, and Spanish dictionaries, locale normalization, and English fallback. `src/i18n/provider.tsx` resolves browser preference on initial client mount and persists the selection in localStorage and the same-site `ora-locale` cookie; `src/i18n/request.ts` validates the cookie for API responses. Add translations to every dictionary and run `npm run check:i18n`.
- `src/lib/`: auth, access control, Prisma, and domain utilities. `version-check.ts` performs best-effort stable GitHub release checks with a 12-hour in-memory cache. Initial owner setup is in `src/app/setup/` and `/api/setup`; when owner credentials are not configured, `ensureOwner` creates a temporary account without a password and generates `owner-setup-code.txt` in the app root, which is consumed and removed by the one-time setup flow.
- `prisma/schema.prisma`: data model (`User`, `Team`, `TeamMember`, `Project`, `ProjectMember`, `TimeEntry`, and `Role`) with the fixed SQLite URL `file:./ORA.db`. Migrations are in `prisma/migrations/`. Local SQLite databases (`prisma/*.db`, journal files, and SQLite variants) are excluded from Git; an empty schema is created by applying versioned migrations. The schema must stay in sync with those migrations; do not leave it reduced to only the datasource block.
- `scripts/install.ps1`: elevated Windows installer prompts for an available TCP port on fresh installs and preserves `.env` `PORT` when `OraTimeTrackingService` already exists; checks service state and expected database presence before build/service changes. The final URL and WinSW runner configuration use the same port.
- `scripts/update.ps1`: elevated external Windows updater. Validates existing `.env`, configured port, runner service/XML/install path, listener and HTTP health, database presence, and updater service state before staging. After stopping the runner it checks for remaining processes/SQLite sidecars and validates database integrity when `sqlite3.exe` is available, then hash-checks staged and retained DB copies before activation. It preserves `.env`/custom logos/main service config, migrates a copy of fixed `prisma/ORA.db`, replaces app files with rollback and retains versioned prior files/DB. After the main service passes HTTP health checks, it installs or refreshes `OraTrackingServiceUpdater` from verified release scripts; legacy installations without a broker require an elevated external update. The auxiliary service's durable status in `%ProgramData%\\Ora` is retained. Emits coarse update phases to a durable status file. IIS remains administrator-managed.
- `scripts/updater-agent.ps1`: constrained local broker run as the `OraTrackingServiceUpdater` Windows service. Accepts only fixed `status`/`start` commands over a restricted named pipe, pins the install path and status file at install time, and delegates execution to `scripts/update.ps1`. Does not accept arbitrary commands or paths.
- `scripts/deletion-agent.ps1` and `scripts/deletion-run.ps1`: constrained `OraTimeTrackingDeletion` broker and fixed uninstall worker installed under `%ProgramData%\\Ora\\deletion`; the worker pins the app path, reports durable status under `%ProgramData%\\Ora`, requires the Owner-only API's explicit confirmation, optionally exports Excel before removal, and removes the deletion broker last. The Owner must first download the full Excel backup; uninstall inventory export and data preservation are separate choices. Installer repair must refresh the broker scripts and use the same fixed Documents export path; durable status is retained until broker deregistration is confirmed. It is separate from Ora Desktop; Windows lifecycle validation remains mandatory.
- `scripts/updater-client.ps1`: local client for the named-pipe updater broker, used by the web app to query status and request updates.
- `scripts/publish-release.ps1`: repository release helper; bumps `package.json`, Tauri config, Cargo manifest and lockfile in sync, adds the desktop release marker, publishes the server release and dispatches the desktop installer workflow. Release and installer publication require explicit user confirmation; workflow completion remains asynchronous. The local ignored `.release-changelog.md` tracks cumulative user-facing release notes from the 2.0.0 baseline; when asked for release notes, review changes since that baseline and provide a complete changelog without implying publication.
- `README.md`: user and product documentation; keep it up to date. Keep production hosting and reverse-proxy guidance accurate, noting the installer manages Ora's Windows service while IIS remains administrator-managed. From this point through the end of the project, keep it modern, scannable, and visual using **pure Markdown** plus local images: a short intro, a jump list, GitHub-style tables, blockquote callouts, fenced code, and colored cards. Color belongs in image files under `docs/readme/` (SVG), referenced with Markdown image syntax such as `![Track](docs/readme/track.svg)`. Do not use raw HTML (`<table>`, `<td>`, `<p align>`, `<img>`, `<br>`, `<div>`): the in-app viewer prints those tags as text. Do not revert it to long unbroken prose. Preserve accuracy when restyling; user-facing facts stay in the README, developer conventions stay here.

## Development conventions

- Keep TypeScript strict and follow existing App Router patterns.
- Preserve roles and authorization checks in APIs: hiding a UI item is not a security control.
- For Prisma schema changes, add a new migration and do not modify migrations that may already have been applied. Check whether the client needs to be regenerated.
- Keep the UI consistent with CSS variables (`--bg`, `--surface`, `--ink`, `--muted`, `--line`, `--brand`, `--good`, `--warn`, `--danger`, etc.); avoid hardcoded surface and text colors where they should adapt to themes.
- Light presets are `ora-default`, `ora-blue`, `ora-green`, `ora-purple`, and `ora-orange`; `dark` is a single theme. `NEXT_PUBLIC_ORA_THEMES` controls which additional presets are exposed, while `ora-default` is always allowed. Validation and UI use the same list from `src/lib/app-config.ts`. The active theme is applied on `html[data-theme]`; preferences are stored in localStorage (`ora-theme`, `ora-light-theme`).
- `.env` is the central source of runtime/build configuration; add every new option here and document its key in `.env.example`. Settings exposed to the client must use `NEXT_PUBLIC_*` and are embedded in the bundle. Avoid parallel hardcoded configuration in application files.
- `NEXT_PUBLIC_APP_NAME`, `NEXT_PUBLIC_APP_TAGLINE`, `NEXT_PUBLIC_APP_DESCRIPTION`, `NEXT_PUBLIC_APP_LOGO_LIGHT`, and `NEXT_PUBLIC_APP_LOGO_DARK` configure branding. Custom logos must be placed only in `public/custom/`, which is ignored by Git; configure only `/custom/...` paths (never URLs or other paths). If only one logo is set, it is used for both modes.
- The global header and side panel are in `Shell`. Management links are restricted to owner/admin.
- Avoid destructive data changes and do not overwrite unrelated work.
- Do not claim a development server is running or verified unless you have checked it; respect user requests not to check or restart it.
- All comments and developer-facing documentation, including this file, must be written in English. User-facing text belongs in the typed dictionaries in `src/i18n/messages.ts`; do not add new hardcoded interface strings.

## Report exports

- UI: `src/app/(app)/manage/report/page.tsx`; endpoint: `src/app/api/export/route.ts`.
- Repeated `userId`, `projectId`, and `teamId` parameters are deduplicated server-side. Different filters intersect (AND), values within one filter are combined (OR); the query has no row limit and returns each entry once. Entries API requests for USER remain constrained to `me.id`; export is restricted to OWNER/ADMIN.
- Date filters use the start timestamp; the UI includes the full final date through the last millisecond.
- `focus` determines grouping by `project`, `team`, or `user`; repeated `column` parameters are validated against the `FIELDS` whitelist.
- CSV: a single item is returned as CSV, multiple items as a ZIP containing separate CSV files (fflate). Excel: one worksheet per item, with unique names limited to 31 characters.
- Report UI and exported CSV/Excel labels, fallback values, date/number formats, and validation messages are localized according to the validated `locale` query parameter; internal column keys remain stable. Update README and the history when export behavior changes.

## Roles and themes

- Report/export APIs require a manager (`isManager`); entries queries always force `userId: me.id` for standard users.
- `ora-theme` and `ora-light-theme` preferences live in localStorage, persist after logout, and are validated against supported presets in the layout and Shell.
- There is one OWNER per installation: `ensureOwner` uses `.env` credentials only during initial provisioning and repairs legacy duplicate owners by demoting subsequent accounts to ADMIN. Any authenticated user can change their own password through `PATCH /api/account` after verifying the current password; only OWNER can change other users' email addresses and force password resets through `PATCH /api/users/[id]`. A reset sets `passwordHash` to `null` to allow the first-access flow; always protect the OWNER account.
